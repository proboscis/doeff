# 責務分離の失敗例: doeff の pin を上げるだけで、呼び手が枠の終了コード 75 を覚えなければならなくなる

失敗例を 1 つ見つけ、実際に再現しました。pin を上げる作業は配線だけで済むはずですが、実際には dotfiles の別の責務を持つ呼び手 2 つ(commit の hook と日次の段)の判定を変えなければなりません。

## 1. 変更の要求と、それが要る理由

**要求:** dotfiles の agentcli が宣言している doeff-linter の版(`agentcli/pyproject.toml:187` の rev `5b35e216`、10-11)を、枠の門が入った版(`86ecd1344` 以降)へ上げます。

**理由:**
- pin はふだんから上げています。
- R1 は「会話が撃つ道の linter が枠に入る」ことを求めています。会話が dotfiles に commit すると、pre-commit の hook が `doeff-linter --commit-hook` を撃ちます。これも撃つ道の 1 つで、pin を上げれば枠に入るはずの道です。
- 今の pin が門を含まないことは実測で確かめました(`git merge-base --is-ancestor 86ecd1344 5b35e216` が偽)。

**前提は守っています:**
- 1 枠 = 検の process 木 1 つのままです。
- 値は json の宣言だけが持ちます。
- env で値を替える口は作っていません。
- 再現では宣言の写しを K = 1・待ちの上限 3 秒にしました。R1 自身が「宣言の写しで K = 1」と書いており、doeff の検と同じ手です。上限の秒は短くしただけで、通る道(上限で 75 になる道)は本番の 1200 秒と同じです。

## 2. 関係する主張と、予想に反して変わる所

**元の主張:**
- 呼び手(M-callers)は「枠の事」を持たない。例外は日次の段の宣言だけ。
- check_slot.rs の頭の註: 「binary の起動の 1 点で取れば、どの道から撃っても同じ枠に入る」。道ごとに呼び手を変える必要は無い、という意味です。
- M-cli が公開するのは「CLI」とだけあり、終了コードは書かれていません。

**予想では** pin の行と uv.lock だけが変わります。

**実際に変わらなければならない所:**
- **`agent/hooks/pre-commit`(dotfiles)**
  - 責務は、commit を止める検査と、終了コードの契約です。契約は `@exitcode 1` = 新しい当たり、`@exitcode 97` = 測れない(未実行)です(9〜12 行)。
  - 194〜199 行は 0 でない値を全部「新しい当たり」と読み、終了 1 を返します。
  - 枠の待ちの上限切れ(75 = 未実行)も「新しい当たり・終了 1」になり、自分の契約(未実行は 97)を破ります。
- **`agent/tests/doeff_linter_agentcli.py`(dotfiles の日次の段)**
  - 頭の註の契約は「0 = 当たり無し・1 = 当たり在り・ほか = linter の失敗で赤」「当てられなかった時は `check-unexecuted:` の行と 97 を出し、緑とも赤とも数えない」です。
  - `judge`(100〜106 行)は 75 を `Linted(75)` にします。結果、未実行が「赤」として出ます。
- **agora の `land_lint_gate.hy`(一覧に載っている呼び手)**
  - 閉じた語彙(0・1・3・4 以外は動かなかった物)で読むので、結果は「測れなかった」になり、危険ではありません。
  - ただし理由は「linter が動かなかった(終わりの code 75)」と誤って出ます(184〜191 行・report-line)。これはコードを読んで判断したもので、実行はしていません。

## 3. 何がどこへ漏れているか

**漏れている知識:** 「75 は、枠の待ちが上限を越えて命令を走らせなかった事(未実行)を表す」。これは正本 M-canon の方針です(`machine_check_slots.py:69-70`、216-217 行「未実行の印(検の赤ではない・合格でもない)」)。

**漏れる道:** M-gate は `check_slot.rs:157` で `Command::exec` を使い、linter の process を正本の `run` に置き換えます。そのため linter の終了コードは、そのまま正本の終了コードになります。M-gate は戻ってこないので、75 を linter 自身の語彙に訳し直す場所がありません。exec を選んだのは、pid を保ったまま信号と時間切れを届けるためです。その代わりに、終了コードの語彙の持ち主を手放しています。結果として、終了コードを分類する呼び手は全員、75 の意味を自分で覚えなければなりません。

**4 種の区別:**
- **配線の変更:** pin と uv.lock。予想どおりで、欠陥ではありません。
- **共同の不変条件:** 「未実行は緑とも赤とも数えない」。系全体で共有してよい不変条件です。問題はその表し方が呼び手ごとに違う事です。
  - 正本: 75 と `check-slot:` の行
  - dotfiles: 97 と `check-unexecuted:` の行(remote_check に「写しを呼び手側へ置かない」とあります)
  - land_lint_gate: 2 と 4
- **公開契約の拡張:** M-gate の註(55〜56 行「上限の 75 で commit は止まって出し直せる」)を見ると、75 が呼び手に届く事は意図されていたと読めます。もし拡張なら、それ自体は正当です。ただし次の 2 点が抜けています。
  - M-cli の公開契約に 75 が書かれていない。
  - 「M-callers は枠の事を隠す」は成り立たず、終了コードを分類するすべての呼び手(一覧に無い dotfiles の 2 つも含む)が変わる、という予測が主張に無い。
- **隠すはずの知識の漏洩:** 直し方は 3 つ考えられますが、どれも 1 つの module では済みません。
  - 呼び手が 75 を覚える → 枠の知識が呼び手へ漏れます。
  - 正本が 97 と `check-unexecuted:` を出す → dotfiles の契約が正本へ入り、`run` の終了コードの意味も変わります(S3 の前提の外)。
  - M-gate が exec をやめて訳す → 設計の「pid は同じ」と S8 の前提を崩します。

## 4. 最小の再現と、観測した結果(実測)

作業の場所は自分専用の `/tmp/tmp.QX39bxLY26`(`mktemp -d` で作成)です。共有の repo には書いていません。

**用意した物:**
- linter: 機体の wheel の置き場 `/work/state/wheels/doeff-linter-dbfba2ef…/…whl` から取り出しました。`--version` は `doeff 86ecd134…` で、着地の版そのものです。
- `HOME=$T/home` の下に正本の写し(`git show f333bd2f:…/machine_check_slots.py`)と、宣言 `{"slots":1,"dir":"$T/slots","waitLimitSeconds":3}` を置きました。
- `$T/dfrepo`: git の小さな木。`agentcli/pyproject.toml`(DOEFF016)と、新しい当たりの無い変更(`y = 2` を足しただけ)を stage しました。
- `scripts/fragment.sh`: pre-commit の 180〜200 行をそのまま写した物。`hook_run.sh` がこれを撃ちます。
- `scripts/held_run.sh`: 別の process `run --label long-check -- sleep 30` に枠 1 本を持たせたまま、対象を撃ちます。

**再現の手順:**
1. `sh $T/scripts/hook_run.sh $T`(枠が空いている時)
2. `sh $T/scripts/held_run.sh $T $T/scripts/hook_run.sh`(枠が埋まっている時)
3. `sh $T/scripts/held_run.sh $T $T/scripts/judge_target.sh`(日次の段)
   - これは dotfiles の段の `judge`・`report`・`exit_code` を、agentcli の venv(`--no-sync`)で呼びます。

**結果:**

| 場面 | 観測した事 |
|---|---|
| 1) 枠が空いている時の hook | 通る(rc 0) |
| 2) 枠が埋まっている時の hook | 下の stderr が出て、hook は終了 1 |
| 3a) 枠が空いている時の日次の段 | `Linted(returncode=0)`、段の終了 0 |
| 3b) 枠が埋まっている時の日次の段 | `Linted(returncode=75)`、report は「doeff-linter の終了 75(0 = 当たり無し・1 = 当たり在り)」、段の終了 75(未実行の 97 ではない) |

2) の stderr:
```
check-slot: …の待ちが上限 3 秒を越えた…— doeff-linter --commit-hook dfrepo (…) は未実行
pre-commit: agentcli の層の規則に新しい当たり(exit 75)— commit を断る(#3908)。
```

**見るべき点:** 中身が同じ変更で、枠が空いていれば通り、埋まっていれば次のように読まれます。
- hook は「新しい当たり」と読み、終了 1 を返す(契約では 97 のはず)。
- 日次の段は「linter の答え(赤)」と読む。

正本自身は同じ時に「未実行」と名乗っており、hook の出力と食い違っています。

## 5. 確かめていない事・足りない情報

**推測(コードと註を読んだだけ):**
- 着地の窓は、段の rc 75 を赤と数えると思われます。remote_check の註「窓は rc 97 ∧ 申告行で未実行を立てる」からの推測で、窓は実行していません。
- land_lint_gate の 75 の扱い(上の 2 の 3 つ目)も実行していません。

**未確認:**
- 本番で 1200 秒の待ちが実際に起きる頻度。
  - 会話の道具の 1 命令の上限は 600 秒なので、会話の中の対話的な commit では道具が先に切ります。75 が出るのは、long-command・script・日次のように 600 秒の外で撃つ道です。
- 日次の Pod の `$HOME/dotfiles` に正本が在るか。無ければ門は何もしないので、3b は本番では起きません。
- pin を上げる予定が実際にあるか。
- 75 を linter の CLI の契約として意図していたか。M-gate の註からは意図していたと読めますが、M-cli の公開契約には書かれていないので判断できません。

**範囲:** 実行したのは上の 3 つの再現だけです。cargo test・pytest の全体、他の会話への連絡、共有の repo への書き込みはしていません。一時の dir(取り出した 14 MB の binary を含む)は残してあり、消してかまいません。
