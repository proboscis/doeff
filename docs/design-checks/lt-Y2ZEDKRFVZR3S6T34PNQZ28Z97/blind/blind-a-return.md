# 盲検 A の返答: 責務分離の失敗例(lt-Y2ZEDKRFVZR3S6T34PNQZ28Z97)

**要旨**: 失敗例を 1 つ見つけました。鍵 1 つに同時に使われる macro の環境が 16 を越えると、準備の焼き直しが元の事故の形に戻ります。直すには、S2 が「変わらない」とした M1 を変える必要があります。正しい直し方を決める材料は M2・M3・M4 と運用の側にあり、M1 の外に散っています。

## 1. 変更要求と、それが要る理由

- **変更要求(運用の変更・S2 の適用範囲)**: doeff-hy の macro を直す card を、同じ worker の上で並べて配ります。card scheduler の天井は 50 です。各会話の作業木は `DOEFF_HY_CODE_STORE` を worker から継いだまま動きます。その状態でも R1・R2(準備が 2 回目から焼き直さない)を保つ、という要求です。
- **要る理由(実測)**: macro の変更は今いちばん多い仕事です。
  - `git log` で数えると、`packages/doeff-hy/src/doeff_hy` に触れた commit は 10-11 に 22 本、10-12 に 6 本ありました。
  - そのうち `macros.hy`・`binding_forms.py` に触れたものは、10-11 に 10 本、10-12 に 4 本です。
  - この会話の Pod の `DOEFF_HY_CODE_STORE` は `/work/state/doeff-hy-code-store` でした(echo で確認)。会話の作業木の import は本番の保存先へ書いている、ということです。
- **macro の環境が増える経路(コードを読んで確認)**: 作業木で macro を直すと、使い手の `.pyc` は source に合ったまま、記録だけが古くなります。この時 M3 は保存先を引かずに compile し直して `add_code` します(`loader_hooks.py` の 382→399→408→409 行。`_from_shared_store` は 496 行で先に None を返す)。
  - そのため、検を 1 回走らせるごとに、使い捨ての新しい記録の entry が「いちばん新しく使った物」として鍵ごとに足されます。

## 2. 関係する主張・前提と、予想に反して変わる物

- **元の主張**
  - S2: 書き手が 3 つ以上でも、新しい種類の書き手が加わっても、M1・M2 は変わらない。変わるのは新しい書き手の module と配線だけ。
  - S1: 上限と除く順は M1 だけが持つ。
- **前提は守っています。** 呼び手は M3・M4 だけで、どちらも `current_code`・`add_code` を通ります。照らしは呼び手が渡し、M1 は記録の欄を読みません。worker の版上げの後の話です。
- **予想に反して変わる物**
  - **M1 の `CODE_ENTRIES_PER_KEY = 16` と、使った時刻の古い順で除く決まり**: 上限を越える数の環境が同じ鍵を交互に使うと、毎回すべてが外れます(4 の実測)。準備の entry は、使い続ける他の環境と使い捨ての環境を合わせて 16 個が後から使うと押し出されます。
  - **ずっと押し出されないように直すには、M1 だけでは決められません。** 次のどれかが要ります。
    - M4 の entry を守る口を M1 に足し、M4 がそれを使う(M1+M4)。
    - M3 が使い捨ての環境の code を足さないようにする。何が使い捨てかの判断が新しく要ります(M3+M2)。
    - 「足しただけで一度も使われていない entry を先に除く」。この場合 M1 は使った時刻と足した時刻の 2 つを持つ必要があります。ところが今 entry の状態は file の mtime 1 つだけで、M5 がそれを「使った時刻」として 7 日の判断に読んでいます(M1+M5、または M1 だけで無理な形)。

## 3. どの知識がどこへ漏れているか

上限の正しい値は、次の不等式で決まります。

`上限 ≥(同時に使われる macro の環境の数)×(環境ごとの記録の通り数)`

右辺はどれも M1 の外の知識です。

- **隠すはずの知識の漏洩(M2 → M1)**: 「同じ環境でも記録が 2〜3 通りになる(import の途中の digest は None、展開で実行された関数の印は process に依る)」は M2 の内部の知識です。これが M1 の定数の根拠として `code_store.py` の 57〜61 行に書かれています。
  - このため、M2 の記録の形の変更(S3 — 欄を足す)が環境ごとの通り数を増やすと、M1 も検も変えないまま実質の席が減り、R1 が崩れます。S3 の「M1 不変」は、指紋が潰れないという意味でしか成り立ちません。
- **漏洩(M3 の足し方 → M1 の除き方)**: M1 の除き方は「新しく使った物ほど生きている」という前提に立っています。M3 は使い捨ての環境を最新の entry として足すので、この前提は M3 の決めで崩れます。
- **運用の知識 → M1**: 同時に動く会話の数と、版ごとに macro がどれだけ変わるかです。
- **共同の不変条件**: 上の不等式は、設計の表 §2 の M1 の不変条件(entry 数 ≤ 上限という上側だけ)にも、§4 の強制方法にも載っていません。強制されていません。
  - R2 の検は書き手 2 つだけです。単体の検 `test_entries_beyond_the_limit_go_least_recently_used_first` は、使い続けた 1 つを残すかしか見ず、順に回った時の崖は見ていません。
  - M1 自身の註は「少ないと…上書きの取り合いに戻る」と書いており、表の S2 の主張と食い違っています。
- **区別**
  - 意図した公開契約の拡張: M4 の entry を守る引数を `add_code` に足すこと。これは正当ですが、S2 の予想(M1 不変)は外れます。
  - 配線の変更: 上限を環境変数にして boot.sh から渡すこと。これでも M1 は変わり、値を決める知識は外に残ります。
  - 隠すはずの知識の漏洩: 上の 2 点(M2 → M1、M3 の足し方 → M1)が本体です。
