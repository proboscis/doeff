## 結論

失敗例が 1 つ見つかり、写しの上で再現できました。置き場の配置は、主張では M-store が隠す知識です。ところが M-sweep の `object_files` とその検査が、その配置を直に書き込んでいます。そのため M-store の中だけで配置を変えると M-sweep も直す必要があり、直さないと**提示された検査 34 本は全部通るのに、事実(objects)の上限が黙って効かなくなります**。

## 1. 変更要求とその理由

**変更要求**: 事実の置き場の「1 事実 = 1 file」の配置を変える。本命は、種類ごとに事実をまとめた file(pack)にする変更です。最小の例は、fan の段を 1 つ増やすだけの変更です。

**理由**
- 早い判じで当たった時、`resolve` は file ごと・種類ごとに事実の file を 1 つ開きます。前の形では、種類ごとに塊 16 個を開くだけでした。
  - 実測: `~/repos/agora-controllers` の Hy の file は 2855 本(`git ls-files` で読んだだけ)。
  - 推測: 1 file だけを見る hook の実行でも、種類ごとに数千の file を開く。実際の回数は測っていません。
- 小さい事実も 1 block を使います(`OBJECT_MIN_BYTES` の註)。
- facts_cache.rs の直近 11 commit のうち約半分が、置き場の配置を変えています(1 file から 16 の塊へ、JSON から binary へ、objects の分離)。配置の変更は繰り返し起きている種類の変更です。

**前提は守っています**: R1・R2、1 回で終わる CLI、並走、事実を決める物、置き場が消えても答えは同じ、のどれも変えません。公開の関数(`per_file` など)も変わりません。したがって契約の適用範囲の内です。また S1(符号化)ではなく、表の「M-store が隠す: file の配置」を突く例です。

## 2. 関係する主張と、予想に反して変わる物

**関係する主張**
- M-store は「file の配置」を隠す。
- M-sweep は「事実・表の中身」を隠し、上限を不変条件として持つ。
- その強制は `facts_cache_roots.rs`(16 本)が受け持つ。

**予想と実際**
- 予想では、変わるのは M-store の `object_path`(facts_cache.rs:454-457)だけです。
- 実際に直す必要がある物:
  - M-sweep の `object_files`(facts_cache.rs:323-350)。
  - M-sweep の検査の `stale_object`(facts_cache_roots.rs:282-287)と、一時 file の検査(:336-349)。
  - pack にする場合はさらに、M-store が読んだ時に更新時刻を付け直す処理(`read_object` の 481-491)と、M-sweep が事実を 1 つずつ消す処理(`sweep_over_cap` の 385-396)も直す必要があります。

## 3. どの知識がどこへ漏れているか

**漏洩(本題)**: `object_files` は、M-store の次の知識を直に持っています。
- 深さ: `objects/<種類>.<形>/<頭 2 字>/<file>` の 2 段だけを歩き、その下は file しか数えない。
- 一時 file の名: 「`.` で始まり `.tmp` で終わる」で見分ける(:339)。これは `write_object` が作る `.{name}.{pid}.tmp`(:503)に合わせた物です。

検査の側も同じ古い配置に file を置いて確かめるので、配置がずれても検出できません。

**宣言されていない共同の不変条件**: 「file の更新時刻 = 最後に使われた時刻」という取り決めです。書いて更新時刻を付け直す側は M-store(読みでの付け直しは 6 時間ごと)、それを読んで古い順・10 分を判じる側は M-sweep です。両者で分け合ってよい知識ですが、表には書かれていません。下の実験 2 で食い違いを実測しました。

**区別**
- 配線: `place()` が path を組み、`tend_roots` を呼ぶのは配線です。それだけでは欠陥ではありません。
- 公開契約の拡張: この要求には要りません。直すなら、M-store から M-sweep への内部の契約(事実を、最後に使われた時刻・大きさ付きで並べる/1 つ消す/一時 file を片づける)が新しく要ります。これは意図した公開の拡張ではなく、欠けている内部の契約です。

## 4. 最小の変更例・再現手順・観測結果(実測)

**変更**: 写しの facts_cache.rs:456 の 1 行だけ。
`objects.join(&name[..2]).join(&name[2..])` → `objects.join(&name[..2]).join(&name[2..4]).join(&name[4..])`

**手順**
1. `/tmp/dc-lt3tf-CbuZ` へ写して変更し、指定された 2 つの命令で検査を走らせました。lib 9・roots 16・shared 5・focused 3・hy_index 1 の **34 本が全部通りました**。shared の「cache あり・無しで答えが同じ」も通ったので、答え(R2)は壊れていません。
2. `/tmp/dc-lt3tf-scripts/exp.sh <binary>` を走らせました。中身は次の通りです。
   - 根 a(Hy の file 30 本・DOEFF106)を走らせる。
   - 事実の更新時刻を 30 日前にし、本物の事実と同じ dir に 2 時間前の一時 file を置く。
   - `.swept-cap` を消し、中身の違う根 b を上限 1000 byte で走らせる。

**観測**

| | 元の binary | 1 行変えた写し |
|---|---|---|
| 事実の path の例 | `objects/hy-index.bin/05/b4f9…` | `objects/hy-index.bin/ba/a7/56d3…` |
| 30 日前の事実の残り | 0 | **30** |
| 2 時間前の一時 file の残り | 0 | **1** |
| objects の byte | 19800 | **39600** |
| 置き場の全体の byte(上限 1000) | 25608 | 45408 |

写しでは、上限の片づけが事実を 0 byte と数えるので、事実を 1 つも消しません。

推測: linter を組み直すたびに書かれる約 200MB(コードの註の値)が、上限なしに溜まります。zeus で起きた 62G・7.9G と同じ種類の事故になります。

**実験 2(元の binary のまま)**: `exp_touch.sh` で確かめました。
- 2 時間前に置いた事実 30 個を、根 a の実行が作り直さずに読んだ後も、更新時刻は動きませんでした(30 個とも 1 時間より古いまま)。
- その数秒後、別の根 b の実行の上限の片づけで、その 30 個が全部消えました(30 → 0)。

これは表の「10 分の内の事実は消さない」に反します。検査の註が言う「並走する実行が読んでいる」という意味で読んだ場合です。原因は、M-store の付け直しの間隔 6 時間(`OBJECT_TOUCH_SECONDS`)と、M-sweep の守る長さ 10 分(`IN_USE_SECONDS`)の食い違いです。答えは作り直されるので変わりませんが、その分の書き込みが起きます。

## 5. 未確認の前提と不足する情報

**実測した事**: 上の検査 34 本、2 つの実験、Hy の file 2855 本。

**推測の事**
- pack が実際に求められるかどうか。
- 本物の repo で 1 回の実行が事実の file を開く数。
- zeus の置き場が上限の近くにあるか(本物の置き場には触れていません)。
- 1 世代約 200MB という値(コードの註による)。

**していない事**
- pack そのものは実装していません。2 段の fan はその代わりの最小例です。
- code-quality は走らせていません。読んだ限りでは、その契約は file 単位で、facts_cache.rs 全体が doeff-linter-project の 1 つの file です。そのため 1 file の中の M-store と M-sweep の境界は見えないはずです。

**曖昧な点**: 一時 file の名の決まりは、表で持ち主が分かれています(M-store は「一時 file から rename」、M-sweep は「一時 file」の寿命)。設計者が `object_files` を M-store の一部のつもりで書いたのなら、ずれは表の割り当ての方にあります。どちらにしても、境界は主張どおりではありません。

**読んだだけで検証していない別の候補**
- bincode の知識が他所にもある。
  - M-indexer の検査(cache_form.rs:214、raw_tests.rs:173・307)と M-index の塊の読み書きが、bincode を直に使っています。
  - S1 の「形式」を変えても、M-indexer の検査は古い形式を確かめ続けます。
- 1 process で根は 1 つ、という前提が隠れている。`tend_roots` は process ごとに 1 度しか動かない(`OnceLock`)のに、公開の関数は呼ぶたびに根を受け取ります。

残した物は、1 行変えた写し `/tmp/dc-lt3tf-CbuZ`(4.9M)と、`/tmp/dc-lt3tf-scripts/exp.sh`・`exp_touch.sh` です。build の置き場(1.6G)は消しました。共有の source は変えていません(`git status` は空)。
