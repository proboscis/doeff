doeff 0.8.0 makes a handler one thing: a `def (effect, k)` marked with `@handler`. The handler receives each effect together with `k`, the continuation (the rest of the program from that `yield` on), and what it does with `k` decides what the effect means: resume it with an answer, throw into it, pass the effect on, or drop it and end the run. `@handler` alone now takes a generator `def`, so a handler yields what it hands to the VM: `return (yield Resume(k, v))`. 0.8.0 also supports Python 3.15, passes over handlers that do not accept an effect at about half the cost, runs `Ctrl-C` and `SIGTERM` handlers at once under the Rust scheduler, and brings `doeff-time` 0.1.0 to PyPI. Handlers that return `Resume(...)` without yielding it, lambdas given to `handler()` and plain functions given to `with_handlers` now raise `TypeError` — see **Upgrading from 0.7.0**.

## Install

```bash
pip install doeff            # Python 3.11+: the core (doeff, doeff-vm, doeff-core-effects)
pip install "doeff[hy]"      # + Hy and the handlers written in Hy (files, SQL, processes, cache, …)
pip install "doeff[http]"    # + the HTTP client handlers (Hy and httpx)
pip install "doeff[all]"     # both
pip install doeff-time       # new on PyPI: the time effects Delay and GetTime, with a virtual clock and wall-clock handlers
```

Right after installing, `python -m doeff demo` runs one small program, `digest`, under four handlers: `canned` resumes `k` with made-up values, `trace` sees every effect and passes it on, `budget(1)` lets one effect through and then drops `k`, so `digest` stops midway (`'over budget at Summarize'`), and `live_world` fetches the page over real HTTP. The program stays the same; what each handler does with `k` changes the answer.

The five core packages (`doeff`, `doeff-vm`, `doeff-core-effects`, `doeff-hy`, `doeff-hy-pytest`) share one version number, now 0.8.0, and require each other from `>=0.8.0,<0.9`. Supported Python: 3.11, 3.12, 3.13, 3.14 and 3.15, and the free-threaded 3.14t. `doeff-vm` ships 35 wheels (CPython 3.11 to 3.15 and the free-threaded 3.14t and 3.15t, each for Linux x86_64 and aarch64, macOS x86_64 and arm64, and Windows x86_64) and an sdist. `doeff-time` 0.1.0 needs `doeff>=0.8.0,<0.9` and `doeff-core-effects>=0.8.0,<0.9`.

## Upgrading from 0.7.0

**A handler is `@handler` on a `def`, and nothing else.**

| Code | 0.7.0 | 0.8.0 |
| --- | --- | --- |
| `@handler` on a generator `def` | refused: `handler must return DoExpr … got: <class 'generator'>` | the way to write a handler |
| `@handler @do` on a generator `def` | the way to write a generator handler | still runs; deprecated (the repository's semgrep refuses it outside the tests) |
| `return Resume(k, v)` (or `Transfer`, `Pass`, another control expression) from a `def` without `yield` under `@handler` | the VM ran the `Resume` for you | `TypeError: … returned Resume(...) without yielding it`; write `return (yield Resume(k, v))` |
| `handler(f)` where `f` is a lambda, a `functools.partial` or bound method of a plain function, a callable instance or a builtin | — | `TypeError: … is not a handler body` |
| `with_handlers(...)` or `stacked_handlers(...)` given a callable not made with `@handler` or `defhandler` | passed through `handler()` | `TypeError: … is not a handler`, raised where the stack is built |

- A `def` without `yield` under `@handler` still answers the handled block with the value it returns.
- `handler(f)` takes a `@do` function, or a `functools.partial` or bound method of one, as it is.
- A handler that reinstalls the inner handlers it read with `GetHandlers(k)` uses `doeff.handler_utils.reinstaller(h)` instead of `handler(h)`.
- Code that has to run on both 0.7.0 and 0.8.0 can keep `@handler @do` until it drops 0.7.0.
- `doeff_gemini.default_gemini_cost_handler` is now a handler, so `handlers=[default_gemini_cost_handler, ...]` keeps working; `production_handlers(cost_handler=...)` still takes a raw `(effect, k)` dispatcher.

**doeff-hy: `<-` and `!` refuse a bind whose value can be a plain literal.** Binding `None`, `True`, `False`, a number, a string, a keyword or a list / tuple / dict / set literal — as the expression itself, as a branch of `if`, as a value of `cond`, or as a `when` / `unless` — stopped the run with `TypeError: yield got None …` whenever that branch was taken. It is now a `SyntaxError` when the macro expands, and the message names the literal and the fix: wrap the value in `Pure` (`(<- x (if c (Pure None) (f)))`), or bind it without `<-` (`val`). A literal elsewhere, such as an argument of a call (`(<- x (f (if c None 1)))`), is not refused.

**doeff-agents (in this repository): the public API is its effects and its handlers.** `from doeff_agents import …` gives the effects (`doeff_agents.effects`), the values they carry and the handler factories (`doeff_agents.handlers`), 151 names in all. The 69 names that drove a session directly, such as `launch_session` and `monitor_session`, are no longer exported; `doeff_agents.session` and `doeff_agents.monitor` are internal, and `doeff_agents.programs` and `doeff_agents.v2` are removed. In place of `production_handlers`, `mock_handlers`, `default_agent_handler` and `headless_claude_agent_handlers`, install `claude_agent_runtime_handlers(...)` (or `fake_claude_agent_runtime_handlers(...)`), `mock_agent_handlers(sessions=...)` or `scenario_agent_handler(scripts=...)`. `doeff-agents` on PyPI (0.1.1 and 0.1.2) was built for doeff 0.4 and does not change; `pip install doeff-agents` still installs it together with doeff 0.4.

## Other changes since 0.7.0

- **Python 3.15.** `doeff-vm` builds with PyO3 0.29 and ships cp315 wheels for Linux, macOS and Windows, and the five core packages declare 3.15 in their classifiers.
- **Faster dispatch.** A `perform` or `Pass` skips the handlers whose type annotation does not accept the effect in one search, and each handler remembers per effect type whether it accepts it, so a handler that an effect passes over costs about 0.1–0.2 µs instead of 0.3–0.4 µs.
- **`state()` runs inside the VM.** `Get` and `Put` are answered by `doeff_vm.StateHandler` instead of a Python handler, with the same answers: a missing key reads `None`, and other effects pass on. The handler keeps its name `state.<locals>.handler` in tracebacks and in `UnhandledEffect`.
- **Signals under the Rust scheduler.** It waits for an outside completion in 50 ms slices and runs Python's signal handlers between them, so a `SIGTERM` or `Ctrl-C` handler runs at once instead of up to 30 seconds later.
- **Messages and docs say how to write a handler.** An `(effect, k)` `@do` function applied to a program (`fetch_handler(prog())`) raises "… it is a handler body, not a function that builds a program … Mark its def with @handler in place of @do", and the hint of an `UnhandledEffect` reads "install a handler for Fetch: run(fn(prog)), where fn is a def (effect: Fetch, k) marked with @handler …". The README and the docs write every handler as `@handler` on its `def`, and call the handlers of `doeff_core_effects` reference handlers, not built-in ones.
- **Types.** A `defhandler` with arguments (a handler factory), `http_production_handler` and `http_fixture_handler` are annotated to return `doeff.program.ProgramHandler`, so type checkers and `inspect.signature` read them as handlers. Every public name of `doeff` has a docstring, and the API reference has an index of them.
- **PyPI metadata.** Each core package's summary starts with "Algebraic effects for Python:", the keywords are `algebraic-effects`, `effects`, `effect-handlers`, `handlers` and `continuations`, and each package links its Documentation, Changelog and Issues.
- **`doeff-time` 0.1.0** is the first release of `doeff-time` on PyPI. It gives the time effects `Delay` and `GetTime` and three handlers: `sim_time_handler(start_time=...)` (a virtual clock), `async_time_handler()` (the wall clock on `asyncio`) and `sync_time_handler()` (the wall clock, blocking the thread). It is released on its own tag, `doeff-time/v0.1.0`.
