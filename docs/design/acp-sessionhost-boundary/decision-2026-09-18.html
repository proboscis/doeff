決定 — context ごとの成果物の割り

決めた人: operator / 日時: 2026-09-18 / 場で: この設計の会話 改訂する物: agora-redesign/docs/design/bounded-contexts-2026-09-11.md の E(配置)と D(郵便)の置き場

決めたこと

決定 1 — 配置と郵便を engine の外へ出し、context ごとに別の成果物にする

配置(Scheduling・7,517 行)と郵便(Messaging・13,301 行)は、いま acp-engine の library に住み、 engine と同じ binary で配られている。これを engine の外の controller にする。 2 つを 1 つの成果物にまとめず、context ごとに分ける。

言語は変えない。 Haskell のまま、Acp.Sdk.WireClient で wire を話す out-of-process の controller になる。 書き直しではなく、成果物の境界だけが変わる。

決定 2 — Acp.Sdk.WireClient を公開の package にする

2 系統の controller(Haskell と Hy)が同じ wire を話すので、Haskell 側の client を 公開の形にする。置き場は ACP の repo のままでよい(client は提供する側の物で、 相手の語彙を知らないので純度を壊さない)。

なぜ

  • 規則との一致: engine は基盤(kinds・行・watch・CAS・RBAC・欄ごとの書き手)で、 運転の方策は controller。配置も郵便も方策であって基盤ではない。
  • 2026-08-17 の裁定が成果物の水準でも成立する: 「src/Acp へ運転政策を足さない」は 今日、実行時にしか成立していない(installedApps は空・daemon は Scheduling を呼ばない)。 library と binary には 20,818 行の方策が同居している。
  • 版が切り離せる: 配置の方策(profile の梯子・会社の境界・予算)は頻繁に変わる。 engine の binary を配り直さずに変えられるようにする。
  • 安い: ADR 0013 O5/O6 の Acp.Sdk.WireClient が「Haskell の controller を engine の外で 走らせる」ために既に在る。client と apiserver が同じ Haskell の型と同じ Aeson の instance を 共有するので、wire への書きは in-process と byte 一致する。
  • context ごとに分ける理由: 責務ごとに版と所有を分けるため。まとめると、郵便を直すために 配置を配り直すことになる。
