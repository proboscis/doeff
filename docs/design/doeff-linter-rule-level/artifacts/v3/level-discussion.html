1. 重大さの決まり方

既知の違反の一覧に載せると重さ(severity)は下がるが、重大さ(level)は下がらない。エディタの違反の欄は「重大さ × 新しく見つかった分 / 既知の分」で数える。 LLM で判定する規則(201〜205)は確率の閾値で warning か info のどちらかになるので、宣言が無いと minor か info にしかならない。

3b. 議論で開いた問い — judgment が effect を起こさない、という決めそのもの(2026-09-29 追記)

operator: "effects are specifically for testability so i dont get why using GetTime would be problematic" / "i dontget why judgment is supposed to not produce effect"。

観点内容
決めの出所agora-redesign #780 の comment 2026-09-27T07:13:09Z(coordinator の席 cisco-c7 の決定・戻せる)。operator の指示はその時「core→intent→protocol」(層の名前)と「環境ごとの handler を作らない」で、役を judgment / program に分けることは operator の指示ではない。席は core = 「業務の判断と Program」を Functional Core / Imperative Shell に倣って「純粋な判断(judgment)」と「intent を出す Program(program)」の 2 つのタグに分けた(dotfiles の助言 controllers-split-first-by-purity「1 file に純粋な code と I/O を混ぜない」が先にあった)。architecture.hy の :roles = judgment「業務の判断をする純粋な関数」・program「intent を出して業務を進める Program」。#800 の段階 4 で「judgment は :effects []」を規則に、L1464 で法に、DOEFF129 で linter に。
実物の例controllers/kanban/core/tag_judgment.hy の decide-tag(card の状態からタグを決める)、controllers/core/kanban_write_judgment.hy の decide-new(書き込みの依頼から WritePlan を決める)、shared/core の derived-id・epoch-ms-of-time(protocol からも使う小さな純関数)。
テストしやすさとの関係無い。judgment が GetTime を起こしても handler の差し替えで試せる。この席が最初に「テストしやすさに直結」と書いたのは誤り。
実際に効いている理由層の import の規則 L1590(#780): protocol は shared/core の 型と judgment だけ import してよく、program は不可。judgment が effect を起こせるなら、protocol が judgment 経由で業務の Program を抱え込める。effect の禁止 L1464(law types-and-judgments-yield-no-effects)はこの穴を塞ぐためのもの。
もう 1 つの理由(弱い)値 → 値の関数は表形式の単純なテストで済む(ergonomics)。testability ではない。
選択肢a. 今のまま(judgment = 純粋・program = effect あり。GetTime が要る関数は program と名乗る)
b. judgment の名は残すが effect の禁止を外す(129 と L1464 を消す。protocol が judgment を import する規則 L1590 を「型だけ」に縮める必要がある)
c. judgment と program を 1 つの役に畳む(b と同じ帰結 + タグの書き換え)
operator の原則(2026-09-29)"what we care is responsibility boundary. not 'program or not'"。effect を起こすかどうかは分類の軸ではない。軸は「どの層がどの責務を持つか」。
この席の見立て(原則を受けて)judgment / program の分け方は責務の境界ではないので linter の対象から外す(129 と L1464 を消す)。L1590 が守りたかったこと(protocol が import した関数を通して業務を抱え込む)は責務の境界で、正しい表し方は「protocol の handler は汎用の effect しか出さない・intent を出さない」— law translation-targets-only-generic-foundation-effects として既に書かれているが、検査が繋がっていない(wired = false)。これを繋ぐことが 129 の置き換えで、繋げば critical の候補。judgment のタグ自体は残しても消してもよい(境界ではないので linter は見ない)。
