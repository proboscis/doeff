反例候補は、**resume で添付と一緒に引き継ぐ欄を追加し、その一覧を名前付き定数へまとめる変更**です。添付の継承を維持しても、提案された検査 (e) は赤になると予測します。以下は提示コードからの推論であり、実行による確認はしていません。

1. **現実的な変更要求と理由**

   添付画像の処理品質を指定する `attachment_options` を charter に追加し、resume 後も添付と設定を一緒に引き継ぎたい。再開前後で画像の扱いが変わらないよう、添付関連の継承欄を同じ一覧で管理します。

   この機能に定数への抽出が必須という意味ではありません。ただし、欄の追加に伴う合理的な整理であり、storage 軸が許容するとした「名簿の綴りの変更」に該当します。

2. **関係する主張と予想外の変更**

   対象は storage 軸の「実装 1 file のみ・冊は 0 行」という主張と、検査 (e) の「`resume-params-of` 内で `MESSAGE-ATTACHMENTS-KEY` が読まれていること」です。

   変更後も、`resume-params-of` は添付をコピーします。しかし、定数名の直接参照が関数外へ移るため、提示された `readers-of` では同関数を読み手として検出できません。実装に加えて、冊の検査方法にも変更が必要になります。

   静的検査であること、Hy/Python 混在、冊内で検査が完結することは変更しません。添付継承に関する law も変更不要です。

3. **漏れる知識と、契約拡張との区別**

   漏れるのは、**コピー対象のキーが関数内に直接列挙されているか、名前付き一覧を経由しているか**という実装上の知識です。

   `readers-of` が測るのは参照の推移的な関係ではなく、各 form 内に対象文字列が現れるかどうかです。そのため、検査が「添付が継承対象である」という条件を「この関数にキーの識別子が直接書かれている」という条件に狭めています。

   `attachment_options` の追加自体は意図した契約拡張です。一方、既存の添付継承を検査するために定数の配置まで追随する変更は、その拡張とは別です。複数ファイルが変わることではなく、隠すと宣言した名簿の表現方法に検査が依存する点が反例です。

4. **最小の変更例・再現手順・観測結果**

   `judgment.hy` の関数外へ一覧を置きます。

   ```hy
   (setv RESUME-ATTACHMENT-KEYS
         #(MESSAGE-ATTACHMENTS-KEY "attachment_options"))
   ```

   `resume-params-of` のコピー対象を次の形に変更します。既存の通常欄とコピー処理は維持します。

   ```hy
   (for [key (+ #("prompt" "model" "effort" "mcp_servers"
                  "session_env" "binding" "expected_result"
                  "context_file" "launch_attribution")
                RESUME-ATTACHMENT-KEYS
                CHARTER-CARRIED-KEYS)]
     (when (in key charter)
       (setv (get params key) (get charter key))))
   ```

   再現時には、既存テストで受理される添付値を charter に設定し、`attachment_options` も与えます。

   - 変更前後で `resume-params-of` を評価し、添付値が同じまま出力に残ることを確認する。
   - 変更後には追加した設定も出力に残ることを確認する。
   - 提案 (e) の検査だけを実行する。

   **予測する結果：** 添付のコピーは維持されますが、`readers-of` の結果に `resume-params-of` が現れず、構造検査は赤になります。関数外の `setv` は提示の `TOP-FORM-RE` の対象でもありません。

   新しい欄の仕様による影響を除いて確認するなら、まず `RESUME-ATTACHMENT-KEYS` を `#(MESSAGE-ATTACHMENTS-KEY)` だけにして同じ抽出を行えます。この段階で同じ不一致が生じる予測です。

5. **未確認事項と限界**

   - 再照準後の検査コードは未提示です。上の予測は、設計 (e) を提示された `readers-of` で実装する場合に限ります。
   - 実際の添付値の型、`resume-params-of` の引数、追加設定を受理するまでの変更範囲は未確認です。
   - 定数参照を追跡する仕組みが別途入るなら、この反例は成立しない可能性があります。ただし、その機能は提示 helper にはありません。

この候補が示すのは、**名簿の綴り方に依存しないという主張と、関数内の直接参照を要求する測定方法の不一致**です。設計全体の承認・不承認を判断するものではありません。
