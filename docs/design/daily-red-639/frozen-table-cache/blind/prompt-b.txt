## 3. 変更シナリオと事前の主張

### S1(axis = effects・適用): 終端の語を 1 つ足す、または既存の語の retryable を変える

- 変更の例: ACP 側の要求で新しい category を足す(例: 機体の退役で切った手番の語)、または context_exhausted を true にする。
- 主張: 変わるのは M1(表)・M2(契約の文)・M3(写し)・M4(改訂の記録)の 4 か所で、これは**共同の不変条件**
  (契約所有の表を実装・文書・写しの 3 か所に置き、黙った変更を赤にする意図した形)。M5〜M8 は変わらない。
- 予想する波及: M1・M2・M3・M4。
- 前提: 表の語は wire の snake_case。M3 は dict の完全一致で比べる。

### S2(axis = storage・適用): 出来事の置き場を替える

- 変更の例: Mac も送り待ちの表(`OutboxEventStore`)へ移す・`FileEventStore` を退役する・段の DB へ直接書く置き場を足す。
- 主張: 変わるのは M5(置き場の実装)と host の組み立ての 1 点だけ。M7(cache の読み手)と M8(検の世界)は変わらない。
  M8 は置き場の物理を持たず、M5 の Protocol を満たす memory の置き場を M6 に渡すだけなので、本番の置き場の選び方に依らない。
- 予想する波及: M5(と host.hy の組み立て)。
- 前提: 置き場はどれも `HeadlessEventStore` の契約(since が stdout の完全な行を返す)を守る。

### S3(axis = simulation・適用): 仮想の時計で cache 維持を決定的に回す

- 変更の例: 模擬環境(agora_sim)や別の検で、時刻を仮想の時計にして cache 維持の周期を再現する。
- 主張: M8 の時刻は `ClockNow`(M8 の世界が答える)と、応答の行を積む時に M8 が渡す `at` だけから決まる。
  M6 の登記簿の時計(既定は壁時計)は `cache-host-probe` の路では読まれない。M5 の `MemoryEventStore` は OS の時計を読まない。
- 予想する波及: なし(M8 の世界だけで決まる)。
- 前提: `HeadlessEventAppend.at` は呼び手が渡す(M5 の docstring の契約)。

### 不適用

- hardware: この 2 本の検は機体の種類で分かれる判断を持たない(herdr の版の違いは別の依頼書 H)。
- distribution: host_drained の手番を別の host で走らせ直す判断は ACP 側で、doeff 側が持つのは語の表だけ。
  出来事の置き場の cluster 化は S2(storage)で扱う。
- concurrency: M8 は応答の行を積み終えてから読む(単一の thread)。append と since の並行は M5 の契約で、
  その検(`test_sessionhost_headless_events.py`)はこの変更で触れない。
