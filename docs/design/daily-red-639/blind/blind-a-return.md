反例候補は、**遅い機体で watchdog が停止させた検査を、既存の日次ログから名前付きで報告する要求**です。M7 だけで対応できるという予測に、入力情報の不足があります。ただし、複数責務の混在そのものを実証したわけではありません。

1. **現実的な変更要求と理由**

   日次の実行先を遅い Linux 機へ移しても、C 拡張内で停止した検査について、どのファイルの検査が中断したかを報告する。残りの検査が実行されなかった原因を特定するために必要です。

   POSIX、根の `pytest -q`、C 拡張の停止は watchdog が終了させる、という既存の前提を維持します。新しい出力形式や外部サービスは要求しません。

2. **元の主張と、予測を超える変更範囲**

   固定資料の S7 は、M7 の変更だけで「中断した session は必ず名前が出る」としています。M7 の契約は、最後に見えた検査ファイルか、時間切れのスタックにある検査名を使うものです。

   しかし、根の `-q` 実行では開始見出しが出ず、最初の検査が完了する前なら進捗の名前もありません。さらに、現在の M6 の watchdog メッセージには検査名もスタックもありません。

   この場合、M7 の解析だけではファイル名を復元できません。例えば M6 に実行中の node ID を保持・通知させ、M7 にその情報を読ませる変更が必要になります。

3. **漏れる知識と、契約拡張との区別**

   不足している知識は「現在どの検査を実行しているか」です。これは pytest の実行側が持ち、ログ解析側は持ちません。

   M7 がこの不足を実行順や既知の母集団から推定して補うなら、実行側の知識が解析側へ漏れます。一方、実行側が識別情報を明示的に渡す修正は、**正当な公開契約の拡張**です。共同の不変条件である「中断を名前付きで残す」を守るための変更であり、変更ファイルが増えること自体は欠陥ではありません。

   反例が突くのは、必要な情報の受け渡しを追加せずに「M7 だけ」とした変更範囲の予測です。

4. **最小例・再現手順・観測結果**

   最小ケースは、根の `-q` 実行で、最初の検査が C 拡張内から戻らず watchdog が作動する場合です。現在の watchdog が生成する内容は、例えば次だけです。

   ```text

   ```

   異なる二つの検査ファイルでこの状態になっても、このメッセージは同一です。開始見出し・検査名・終了集計がなければ、M7 は両者を識別できません。

   [限定検証ファイル](/tmp/wt639-blind-A/tree/.blind639/test_m7_evidence.py)を追加し、次の2件だけを実行しました。

   ```sh
   uv run --no-sync pytest -q -p no:cacheprovider \
     .blind639/test_m7_evidence.py::test_quiet_run_has_no_session_header \
     .blind639/test_m7_evidence.py::test_watchdog_message_has_no_test_identity
   ```

   **実測：2 passed、1 warning。** `-q` では開始見出しが無効であること、実ソースから取り出した watchdog 関数の出力に識別情報がないことを確認しました。SIGKILL は替え玉に置き換え、本物のプロセス終了は行っていません。警告は、名指し実行で収集しなかった ADR に関するものです。
