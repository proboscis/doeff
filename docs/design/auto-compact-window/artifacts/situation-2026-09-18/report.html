会話の圧縮の閾値 — いまの理解と、直し方

対象 = agentd(doeff-sessionhost)が起こす claude 席。2026-09-18 の会社 Mac での実測に基づく。 設計の記録は docs/design/auto-compact-window/(この文書はその artifacts/situation-2026-09-18/)。

一言でいうと

席が「どこで会話を畳むか」を一言も名乗っていないので、文脈がモデルの窓いっぱいまで伸び続けていた。 直そうとしたら、宣言した値がそもそも起動の引数に届かないという別の欠陥が出てきた。 その根は、起こす意図(launch intent)だけが型を持っていないことにある。

1. 何が起きているか(測った事実)

claude は畳む閾値の指定が無いと、モデルの窓(Fable / Opus は 100 万 token)いっぱいまで畳まない。 1 手番の値段は、出力の量ではなく毎手番読み直す文脈の大きさでほぼ決まる。

見たもの 値
稼働中の claude 席のうち --autocompact を持つもの 0 本 / 43〜49 本
直近 24 時間の Fable(API 価格換算の擬似コスト) 15,996u / 15,783 手番
費用の内訳 cache_read 77% / cache_write 13% / output 10%
1 手番の平均の文脈 550,000 token(普通の開発席は 10〜15 万)
600k を超える手番 手番の 42% ・費用の 59%
観測した最大の文脈 967,000 token
日次の Fable 09-15 4,697u → 09-16 13,913u → 09-17 16,976u

出力を削っても効かない。効くのは文脈を畳むことひとつ。

CLI が受ける値は auto か 10 万〜100 万の整数ちょうどで、幅の外を渡すと引数の解釈の段で死に、 その手番は 1 行も吐かずに丸ごと消える(実射で確認済み)。

2. なぜ「直した」はずが直っていなかったか

値は「会話の宣言(charter)」から起動の引数まで旅をする。その途中に、 欄を手で数え直して新しい辞書を作り直す場所が直列に 5 つあった。

どれか 1 つでも新しい欄を載せ忘れると、その道だけ値が黙って落ちる。 誤りも出ず、記録にも残らず、走行係の既定値にすり替わる。

最初の修理は「名簿 1」だけを直していた。だから実際には、会話が何を名乗っても 引数に出るのは既定値ちょうどだった。これは会話履歴を持たない独立した検分が grep -c auto_compact_window を撃って見つけた(host.hy / launch.hy / headless.hy が 0 / 0 / 0)。

3. 根 — 運ぶ物のうち、意図だけ型が無い

同じ層で、型の有無がきれいに割れている。

運ぶもの 出所 型
session の行 agentd が作る SessionRow(frozen dataclass)
host の設定 agentd が作る HostConfig(frozen dataclass)
起こす意図 socket から受け取る なし(素の辞書)

数で言うと、意図を dict と宣言している箇所が 43、行と設定を型で宣言している箇所が 30。 道具が無いわけではない。acp/effects.py には dataclass が 123 個あり、Hy の file も (defclass [(dataclass :frozen True :kw-only True)] SessionRow []) と書いている。 pydantic の類は依存に 1 つも無く、dataclass がこの repo の道具。

つまり、agentd が自分で構築する値には型が付き、受け取る値だけが json.loads の返した 辞書のまま下流へ流れた。型を復号の点で入れなかったので、以後の関数が全部 辞書を受け取る形で書かれた。

型が無いから、意図を丸ごと要る場所は欄を手で数えるしかない。それが 5 つの名簿の正体で、 受け口の関数の説明文は今こう書いてある — 「serde 既定値を再現し、host 所有値を注入」。 型がやっていたことを手でやり直している、と自分で名乗っている。

4. 直し方 — socket で 1 回だけ型にする

process の境界は socket ひとつだけ。そこで文字列を値に変えるのは避けられないので、 型を入れる場所は構造的に 1 点に決まっている。

型は 2 つに割る。行が意図をわざと一部しか覚えていないからで、これは正しい制約である。 手番ごとの資格(認証の札)は行にも記録にも残さないと決まっているし、依頼の本文や添付も 行に置く物ではない。

型 中身 使う所
LaunchIntent 呼び手が宣言する意図の全体 socket の復号 → 引数の組み立て
LaunchOverlay そのうち行に残してよい部分 行への保存 → 蘇生・続きの手番の復元

関数は 1 本 overlay-of : LaunchIntent → LaunchOverlay。 これで「何を落とすか」が型の性質になり、いまの 4 欄の手選びが消える。

5 つの名簿がどうなるか

場所 直したあと
1 charter → 送る JSON 1 点に縮む(他所の文書を自分の型へ訳す — 正当な境界)
2 socket の受け口 消える(復号が型を返す。既定値は型の宣言)
3 蘇生の受け口 消える(同じ復号点)
4 蘇生の混ぜ合わせ 消える(replace(行の Overlay, 呼び手が名乗った欄) の 1 操作)
5 行に残す + 続きの手番 消える(行は LaunchOverlay を丸ごと持つ)

あわせて、いま同じ袋に混ざっている host が所有する値(socket の path・同時実行数・ backend の種類など)を別の値として分ける。混ぜているから素通しにできず、 全欄の列挙が要っていた。

判定の基準

欄を 1 つ足す時、編集点が 1 つで、間違えたら音が鳴るか。

編集点 間違えた時
直す前 5 か所 無音で既定値に落ちる
いま着地している応急処置 1 か所 無音で既定値に落ちる(6 つ目の名簿ができれば同じ)
型を持たせる 1 か所 構築し忘れが検査で赤

いま branch に着地しているのは応急処置で、編集点だけ畳んで「無音」という性質を残している。 だから計画に「6 つ目を止める静的検査を足す」が残っていた。型にすると、その課題ごと消える。

保存の互換は問題ない。行の列は JSON の文字列なので、古い行は欄が少ないまま読めて既定値で埋まる。

5. まだ決まっていないこと — 畳む輪が 2 つある

この系には既にもう 1 つの畳む仕組みがある。会話が「文脈の使用率が何 % を超えたら」を 宣言すると、agentd が温かい session を捨てて記録から会話を組み直す(2026-09-14 の指示による)。

使用率の分母はモデルの窓であって畳む閾値ではない。だから内側の輪が 40 万で畳むと 使用率は約 40% で頭打ちになり、40 より上を宣言した会話では外側の輪が二度と撃たない (実際のコードを呼んで確認済み。既存の検査が使っている宣言値は 70 と 80)。

案 中身 代償
a(推奨) 内側を優先。外側は低い宣言の時だけ撃つ控えにする 出荷済みの機能の効き方が変わる。記録から組み直す要約は出なくなる
b 宣言のある会話には内側を当てない 既存の振る舞いは変わらないが、いちばん直したい席がそのまま伸びる
c 外側を退役させて輪を 1 つにする 出荷済み機能の削除。今回の範囲を超える

推奨は a。 外側が撃つ 70 万付近は、実測で費用の 59% を占める帯そのもの。 内側はそこへ届く前に、安く(その場で要約して session を残して)畳む。 元の指示の目的は満たし、変わるのは手段。ただし出荷済みの機能の効き方が変わる判断なので、 配備の前に決めてほしい。
