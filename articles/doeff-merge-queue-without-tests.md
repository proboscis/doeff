AIに書かせた変更を1日に何百件もmainへ入れると、マージの前のテストが列を詰まらせます。筆者の環境では、1語だけの修正でも、マージの前の確かめに517秒かかりました。確かめからテストを外した後の2026年10月16日は、433件がmainに入り、確かめは中央値5.3秒でした。

その代わり、全体のテストが全部緑になる版は、この1週間に1つも出ていません。この記事は、マージの前の確かめからテストを外した得と失の両方の記録です。doeffが初めての方はdoeffの連載の1本目(公開予定)から、コードは[GitHub](https://github.com/proboscis/doeff)から読めます。

マージキューは、変更を1件ずつmainの先端へ積み直し、確かめてから入れる仕組みです。確かめの部分を、ここでは門(ゲート)と呼びます。門でテストを走らせる形はよくあり、1日に数件なら困りません。

困るのは、Claude Codeのようなコーディングエージェントを何十も並べた時です。

- 変更の数が、1つのリポジトリで1日に100件を越えます。
- 門は1件ずつ順に走るので、1件の秒が件数の分だけ積み重なります。
- 1件517秒なら、1日の86,400秒で通せるのは167件までです。

筆者の環境で最も変更の多かったリポジトリには、2026年10月16日の1日に161件が届きました。

前の門は、テストと検査の束を走らせていました。2026年9月26日には、設計の記録の注の1語だけを変えた変更で、門に517秒かかりました。うち約360秒は、模擬の環境で動かす試験58本の分でした。

## まず短いコード — 門をハンドラにする

マージキューの1件分の仕事を、doeffで書いてみます。doeffは、処理の中の「積み直す」「確かめる」といった操作を、外側の部品で差し替えられるPythonのライブラリです。

```python
from dataclasses import dataclass  # 依頼を、書き換えないデータ型で表す。

from doeff import Effect, Pass, Resume, do, handler, run, with_handlers  # 依頼・再開・委譲と実行を使う。


@dataclass(frozen=True)  # 発行した依頼を書き換えない型にする。
class Rebase(Effect):  # 「変更をmainの先端へ積み直したい」という依頼。
    change: str  # 積み直す変更の名前。


@dataclass(frozen=True)  # 発行した依頼を書き換えない型にする。
class Gate(Effect):  # 「積み直した木を、門で確かめたい」という依頼。
    files: dict  # 積み直した木(ファイル名から中身を引く)。


@do  # 呼ぶと、1件を入れる手順(Program)ができる。
def land(change):  # 変更を1件、mainへ入れる。
    files = yield Rebase(change)  # mainの先端へ積み直す。衝突したらNoneが返る。
    if files is None:  # 積み直しで衝突したら、
        return "rebase-conflict"  # mainへ入れない。
    if not (yield Gate(files)):  # 門が通さなければ、
        return "gate-red"  # mainへ入れない。
    return "landed"  # 門を通ったので、mainへ入れる(ここでは結果だけを返す)。


@handler  # Programに取り付けられるハンドラにする。
@do  # ハンドラもyieldで、再開や委譲を指示する。
def conflict_scan(effect, k):  # 門は、行頭の衝突の印だけを見る。
    if isinstance(effect, Gate):  # 門の依頼には、
        lines = [line for text in effect.files.values() for line in text.splitlines()]  # 木の全部の行。
        marked = any(line.startswith(("<<<<<<< ", ">>>>>>> ")) for line in lines)  # 印の行があるか。
        return (yield Resume(k, not marked))  # 印が無ければTrueを返す。
    return (yield Pass(effect, k))  # 担当外の依頼は、外側のハンドラへ渡す。


@handler  # Programに取り付けられるハンドラにする。
@do  # ハンドラもyieldで、再開や委譲を指示する。
def sample_repo(effect, k):  # テスト用に、決めた積み直しの結果を答える。
    if isinstance(effect, Rebase):  # 積み直しの依頼には、
        trees = {"fix-typo": {"README.md": "# Hello\n"},  # 1語を直しただけの変更。
                 "left-marks": {"app.py": "<<<<<<< HEAD\nx = 1\n=======\nx = 2\n>>>>>>> fix\n"},  # 印を残した変更。
                 "clash": None}  # 積み直しで衝突する変更。
        return (yield Resume(k, trees[effect.change]))  # 決めた木を返す。
    return (yield Pass(effect, k))  # 担当外の依頼は、外側のハンドラへ渡す。


for change in ["fix-typo", "left-marks", "clash"]:  # 3つの変更を、順に入れてみる。
    print(change, run(with_handlers([conflict_scan, sample_repo], land(change))))  # 結果を表示する。
```

表示は3行です。

- `fix-typo landed`:1語の修正は門を通り、mainへ入ります。
- `left-marks gate-red`:衝突の印が残っているので、門で止まります。
- `clash rebase-conflict`:積み直しで衝突したので、門まで行きません。

コードの語を、先に整理します。

- `@do`を付けた関数は、呼ぶと実行の手順(`Program`)を返します。
- `yield Rebase(...)`や`yield Gate(...)`は、外側への依頼です。この依頼をエフェクトと呼びます。
- 依頼に答える部品をハンドラと呼びます。届いた依頼`effect`と、止まった処理の続き`k`を受け取ります。
- `Resume(k, 値)`で値を渡して続きを動かし、担当外の依頼は`Pass(effect, k)`で外側へ渡します。

要は、門が`land`の外にあることです。テストを走らせる門に替えても、`land`は1行も変わりません。

筆者は、Claude Codeの会話を最大50並べて、仕事を頼んでいます。会話とは、Claude Codeを画面なしで動かす1つのセッションです。変更は会話が書き、マージキューに載せます。

筆者は、マージの門からテストを外し、確かめを次の3か所へ分けました。

| 確かめ | いつ・どこで走るか | 赤の時 |
| --- | --- | --- |
| 変えた所にかかるテスト | 変更を書いた会話が、列に載せる前に手元で | 直してから列に載せる |
| 積み直し・衝突の印・打ち消し | マージキューが、1件ごとに | その変更を入れない |
| 全体のテストなど25の段 | 4時間ごとに、mainの先端の版で | 入った変更は戻さない |

全体の検証で全部の段が緑だった版だけを、安定版のブランチ`stable`へ進めます。mainは「入った物」、`stable`は「確かめ終わった物」という分け方です。

## マージキューが確かめる3つの事

テストは外しましたが、マージキューが何も見ないわけではありません。1件ごとに、次の3つを確かめます。

1つ目は積み直しです。`git rebase`でmainの先端へ積み直し、衝突したら入れません。

2つ目は、衝突の印の1行です。次のコマンドで、空の場所に試す木を作って確かめられます。

```bash
gate="git grep -n -E '^(<<<<<<< |>>>>>>> )' -- . && exit 1 || test \$? -eq 1"  # 門の1行。印が無ければ0、在れば1で終わる。
cd "$(mktemp -d)" && git init -q && printf 'x = 1\n' > app.py && git add app.py  # 試す木を、空の場所に作る。
sh -c "$gate"; echo "印なし: $?"  # 「印なし: 0」と表示される。
printf '<<<<<<< HEAD\nx = 1\n=======\nx = 2\n>>>>>>> fix\n' > app.py && git add app.py  # 衝突の印を残したまま登録する。
sh -c "$gate"; echo "印あり: $?"  # 印の2行と「印あり: 1」が表示される。
```

`git grep`は、見つけると0、見つけないと1、失敗すると128で終わります。この1行は、見つけた時と失敗した時に1、見つけない時だけ0で終わります。

なぜ印を探すのでしょうか。手元で衝突を直す時、印を消し忘れたままcommitできてしまうからです。gitはこれを止めません。真ん中の`=======`は探しません。Markdownの見出しの下線と見分けられないからです。

3つ目は、打ち消しの確かめです。変更が、直近2日にmainへ入った変更を元に戻していないかを見ます。古い版の上で書いた変更が、他の会話の直しを消す事故を止めるためです。戻すつもりなら、commitの本文に`Reverts:`の行で宣言します。

2026年10月16日に失敗で終わった変更は38件でした。29件が積み直しの衝突で、9件が打ち消しの確かめで止まりました。

## 1件517秒の門は、なぜ詰まるのか

門の秒の差が、列の待ちにどう効くかを確かめます。冒頭のコードの続きとして、時間のかかる門と列を書きます。

```python
from doeff_core_effects.scheduler import scheduled  # 仮想の時計を動かす実行の器。
from doeff_time import Delay, GetTime, sim_time_handler  # 待ちと時刻の依頼と、仮想の時計。


def taking(seconds):  # 門の依頼にseconds秒かける、ハンドラを作る。
    @handler  # Programに取り付けられるハンドラにする。
    @do  # ハンドラもyieldで、待ちや委譲を指示する。
    def slow_gate(effect, k):  # 門の依頼だけを横取りする。
        if isinstance(effect, Gate):  # 門の依頼なら、
            yield Delay(seconds)  # 確かめの時間だけ待つ。
        return (yield Pass(effect, k))  # 依頼は、そのまま外側の門へ渡す。
    return slow_gate  # 作ったハンドラを返す。


@do  # 呼ぶと、列を流す手順(Program)ができる。
def queue(arrivals):  # 届いた順に1件ずつ入れ、各件の待ちの秒を返す。
    start, waits = (yield GetTime()), ()  # 始めの時刻と、待ちの記録。
    for at in arrivals:  # 到着の秒(始めからの秒)の順に、
        now = ((yield GetTime()) - start).total_seconds()  # 今が始めから何秒目かを読む。
        if now < at:  # 前の件が済み、次がまだ届いていなければ、
            yield Delay(at - now)  # 届くまで待つ。
        yield land("fix-typo")  # 1件を入れる。門の時間だけ時計が進む。
        waits = (*waits, ((yield GetTime()) - start).total_seconds() - at)  # 届いてからの秒を足した組を作る。
    return list(waits)  # 各件の待ちの秒を返す。


burst = [i * 75 for i in range(8)]  # 10分の間に、8件が75秒おきに届く。
for seconds in (517, 5):  # テストを走らせる門と、衝突の印だけを見る門。
    program = with_handlers([conflict_scan, sample_repo, taking(seconds)], queue(burst))  # 内側で、門に時間をかける。
    waits = run(scheduled(sim_time_handler()(program)))  # 仮想の時計で、待たずに動かす。
    print(f"{seconds}秒の門:", [round(w) for w in waits])  # 各件が届いてからmainに入るまでの秒。
```

- `taking`は、門の依頼を横取りして、決めた秒だけ待つハンドラです。待った後は`Pass`で、同じ依頼を外側の`conflict_scan`へ渡します。
- `with_handlers`の並びは、先頭が外側です。`taking`を最後に置き、門の依頼を最初に受けさせます。
- `Delay`は「待ちたい」、`GetTime`は「今の時刻を知りたい」という依頼です。答えるのは仮想の時計です。

表示は次の2行です。

- `517秒の門: [517, 959, 1401, 1843, 2285, 2727, 3169, 3611]`
- `5秒の門: [5, 5, 5, 5, 5, 5, 5, 5]`

10分の間に8件が届いただけで、最後の1件は約1時間待ちます。10分に8件は、10月16日に実際にあった一番大きな山です。仮想の時計なので、1時間分の流れが約1秒で終わりました。

![同じ8件を、517秒の門と5秒の門で流す](/images/zenn-use-cases-v0/generated/mergequeue-flow.png)
*8件が10分の間に届いた時の、各件の待ちです。517秒の門では待ちが積み重なり、5秒の門では届いた順にすぐ入ります。*

同じ`queue`に、10月16日に実際に届いた161件の刻を渡しました。517秒の門では、待ちの中央値が2.3時間、最大が7.2時間です。門が1日の96%を使い、深夜にまとめて届いた変更が明け方まで待ちます。5秒の門では、どの件も5秒で入ります。

実際の門の1行は、10月16日の394件で中央値5.3秒、9割が13.2秒以内でした。列に載せてから、mainに入って記録が閉じるまでは、433件の中央値が24秒でした。

本物のマージキューも、doeffで書いてあります。記録・時計・gitの操作をエフェクトにしたので、手元では本物を動かさずに試せます。

## テストはどこへ行ったか

### 変えた所のテストは、書いた会話が走らせる

変更を書いた会話は、自分が変えた所にかかるテストだけを、列に載せる前に走らせます。リポジトリ全体のテストは走らせません。2026年9月29日に測ると、全体のpytestはテストを集めるだけで110秒かかりました。

### 全体のテストは、4時間ごとに別の機械で走らせる

全体の検証は、25の段からなります。pytest・型の検査・リンター・ブラウザでの画面の試験・新しいcloneから揃うかの確かめなどです。2026年10月16〜17日の混んだ回の段の秒を足すと、13,148秒(約3時間39分)でした。一番長い型の検査の段だけは、実測ではなく上限の秒で足しています。変更ごとに走らせる長さではありません。

赤の段があれば、段ごとに作業ボードのcardを1枚立てます。cardは仕事を1件ずつ書く札で、直す仕事として会話へ配られます。mainへの流れは止めません。

### 決めた事は、テストで守る

門に検査を足したくなる場面は、何度も来ます。そこで、マージキューの設定を読むテストを書きました。門の1行が衝突の確かめ以外を含むと、赤になります。門から外した検査が全体の検証の列から消えても、赤になります。

設計の記録をテストとして走らせる話は、ADRを書いて終わりにするのをやめる(公開予定)にあります。

## 途中で試した「60秒だけテストする門」

すぐに衝突の確かめだけにしたわけではありません。2026年9月29日から10月1日まで、門でも少しテストを走らせました。変えたファイルから選んだテストを、合計60秒の予算(テストは40秒)で走らせる形です。予算を越えたら、そのテストを「測れなかった」として通します。

10月1日の記録では、門の自動の確かめは中央値74秒で、60秒に収まったのは30%でした。選んだテストを予算の内で測れずに通した変更は、192件中120件でした。流れを遅くしたうえ、多くの変更を確かめられていなかったことになります。同じ日のうちに、衝突の確かめだけに戻しました。

## うまくいかなかったこと

門は速くなりました。一方で、全体の検証が緑になりません。

![4時間ごとの全体の検証の結末(7日・42回)](/images/zenn-use-cases-v0/generated/mergequeue-verify.png)
*2026年10月11〜17日(UTC)の42回です。結末が出た39回は、赤が20回、判じられないが19回で、緑は0回でした。*

- 判じられないは、時間切れなどで走らなかった段がある回です。残りの3回は、始まらなかったか記録がありません。
- 1回あたりの赤の段は、3〜12個でした。
- このため、`stable`は10月6日の版から進んでいません。10月18日に数えると、mainは`stable`より4,407 commit先にあります。

赤の段ごとにcardは立ちます。けれども、直す速さが、赤の増える速さに追いついていません。緑の印は、赤を直す流れが速くなければ役に立ちません。

ほかにも、次の困りごとがあります。

- 筆者の環境の配備は、`stable`ではなくmainを追います。赤い版が本番に出ることもあります。
- 衝突の印の1行も、混んだ機械では最大66秒かかりました。リポジトリ全体を探すからで、変えたファイルに絞る余地があります。

## まとめ

- 1件ずつ走る門では、門の秒と届く件数の積が1日に近づくと、待ちが時間の単位で伸びます。
- 門は積み直し・衝突の印・打ち消しの確かめだけにしました。テストは書いた手元と、4時間ごとの検証へ移しました。
- 2026年10月16日は433件がmainに入り、門は中央値5.3秒でした。
- 引き換えに、全体の検証が緑にならず、安定版のブランチが止まっています。赤を直す流れの強さが、この形の前提です。
- 門をdoeffのハンドラにしたので、同じ手順を仮想の時計で流し、門の秒の効き目を比べられます。

会話を並べる仕組みの全体は、1人でClaude Codeを最大50並べたら、詰まるのは人だった(公開予定)で書きました。
