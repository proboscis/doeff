Use case: infographic-diagram. 日本語技術記事の完成ダイアグラム。添付は表現トーンの参考のみ。全面が不透明な白、ネイビーの日本語、ティールの明瞭な矢印、薄い青/ミント/紫の平面的な角丸枠。写実・3D・金属・ガラス・立体的装置・台座・装飾的なイラストを禁止。横長3:2。図中に下記の短いコードを大きく正確な等幅文字で配置し、対応する操作や流れと矢印で結ぶ。大きいタイトル、余白、最大6ノード程度。日本語の説明を短く、コードは改変しない。原稿からの抜粋なので小さく「コードは抜粋。完全な例は本文へ」。以下の意味を守り、勝手な挙動や架空のAPIを追加しない。
コードは提供されたもののみ。コード各行の日本語コメントも省略せず表示。機械的な循環矢印や図にないAPIを追加しない。
見出し:依存を求め、受け取った処理をyieldでつなぐ
コード:
@do  # 依存の取得と、取得した処理の実行を合成する。
def make_title(text: str):  # 呼び出し元は具体的な整形実装を渡さなくてよい。
    formatter: FormatTitleFn = yield Ask(FormatTitleFn)  # ハンドラから整形処理を受け取る。
    return (yield formatter(text))  # そのProgramを実行し、見出しの文字列を返す。
図:白背景・平面的な角丸枠・紺文字・青緑の矢印。上か左にコメント付きの4行コード。処理側の流れは「make_title」→「Ask(FormatTitleFn)」→「readerが整形処理を返す」→「yield formatter(text)」→「見出しの文字列」。readerに渡す辞書の選択肢として「plain_title → 新着記事」と「bracketed_title → 【新着記事】」を別の小枠に置き、『どちらかの実装を供給』と明示。2実装を同時実行したり、Askの時点でformatterが実行されるようには描かない。Askから返るのは呼び出せる@do関数、その後のyieldで文字列になるという境界を明確にする。写真・3D・立体的な装置は禁止。
説明:`Ask`で実装を受け取り、その実装が返す`Program`を`yield`します。外側の辞書を替えると、同じ利用側から異なる見出しが得られます。
矢印は意味が確かなものだけ。結果の一覧は独立したカードにして不要な矢印を引かない。
