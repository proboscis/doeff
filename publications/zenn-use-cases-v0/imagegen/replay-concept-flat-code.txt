Use case: infographic-diagram. 日本語技術記事の完成ダイアグラム。添付は表現トーンの参考のみ。全面が不透明な白、ネイビーの日本語、ティールの明瞭な矢印、薄い青/ミント/紫の平面的な角丸枠。写実・3D・金属・ガラス・立体的装置・台座・装飾的なイラストを禁止。横長3:2。図中に下記の短いコードを大きく正確な等幅文字で配置し、対応する操作や流れと矢印で結ぶ。大きいタイトル、余白、最大6ノード程度。日本語の説明を短く、コードは改変しない。原稿からの抜粋なので小さく「コードは抜粋。完全な例は本文へ」。以下の意味を守り、勝手な挙動や架空のAPIを追加しない。
コードは提供されたもののみ。コード各行の日本語コメントも省略せず表示。機械的な循環矢印や図にないAPIを追加しない。
見出し: HTTPの取得と保存を、別のハンドラで合成する
コード:
first = make_memo_rewriter(HttpRequest)(fetch_text(url))  # 再利用を判定
first = sqlite_memo_handler(database)(first)  # 応答を保存
first = fixed_http(first)  # 未保存時だけ取得
図の意味と流れ: 白背景の平面的ダイアグラム。写真・立体・写実的な装置は禁止。3行のコードを左側に大きく配置し、各行から右側の担当ボックスへ細い線を結ぶ。処理本体→HTTP依頼→メモ化の判定。判定からSQLite（MemoExists/Get/Put）へ照会する双方向矢印。保存ヒットの矢印はHTTP取得を迂回して応答→処理本体の続きへ。保存ミスの矢印だけHTTP取得担当へ届き、固定HttpResponse→SQLiteへ保存→応答を返す。HTTP取得担当の交換候補として固定応答と標準HTTPを同じ枠の選択肢で示す。二つを同時実行するように描かない。保存先・取得担当・判定の3つは独立した責務。HttpRequestに対して全ハンドラが順次処理する一本線にはしない。
説明: メモ化の判定、保存先、保存ミス時の取得方法を独立に選びます。
